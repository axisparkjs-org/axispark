# Changelog

All the `@axisparkjs/*` packages are released together and share the same version. This file lists
the changes of each release; it is generated from the changesets when a version is released (see
`scripts/release-notes.mjs`). A changeset that starts with a short bold title, such as `**MCP server.**`,
gives the website changelog the name of the feature to highlight.

## 1.6.1 (2026-11-20)

### Improvements and fixes

- `ConsoleTransport` writes to the standard output through a buffered asynchronous stream (`sonic-boom`, already installed with Fastify) instead of `console.log`, which is synchronous with files and pipes and blocked the event loop under load. The lines still in the buffer are written when the process exits, and when the application is destroyed. New `buffered` option (`false` keeps `console.log`), new `LogTransport.flush()` and `Logger.flush()`, called by `app.destroy()`.
- `CacheProcessor` keeps the generation of each handler read from a store in memory for one second, so a cache hit costs one store read instead of two (one round trip with Redis). `evict()` updates the generation kept in memory immediately; other processes that share the store see the eviction when their copy expires. New `CacheProcessor.setGenerationTtl(ms)` to change the time, or to disable it with `0`.
- `CacheProcessor` protects the cached handlers from cache stampedes: when several requests of the same process miss the same key at the same time, only the first one invokes the handler and the others receive its result. When that invocation fails or its result is not cached, the waiting requests invoke the handler themselves.
- `InMemoryCacheStore` has a maximum number of values, 10 000 by default: when a new value exceeds it, the least recently used value is removed, so many distinct keys can not exhaust the memory. New `maxEntries` option of `InMemoryCacheStore`, and `MemoryStore({ cache: { maxEntries } })` to set it in the plugin options; `Infinity` keeps the previous unbounded behaviour.
- `ClassRegistry.getWithMetadata()` and `getAllByName()` no longer copy and filter the whole registry on every call: the result of each metadata key and name is indexed until a class is registered or removed, or metadata is defined on a class. New `Metadata.version`, a counter that changes every time metadata is defined on a class.
- `ClassResolver` reads the `design:paramtypes` and `@Inject()` metadata of each class once and keeps the tokens of its constructor dependencies, so the scoped and transient resolutions of a known class do not read metadata.
- The Fastify adapter only serves the static files of `<basePath>/public` when the folder exists, so API-only applications start faster and have no static route. New `staticFiles` option to serve them always (`true`) or never (`false`), and `staticFilesOptions` (`root` and `prefix`). `@fastify/static` is still registered without serving files, because the file results use its `reply.sendFile()`.
- `FileTransport`, `RotatingFileTransport` and `DailyFileTransport` keep the file open with a `WriteStream` in append mode instead of calling `appendFile`, which opened and closed the file for every entry. The entries are written in order, the rotating transport counts the size of the file in memory and closes it before rotating, the daily transport switches to the new file when the day changes, and the files are closed by `Logger.flush()` and `app.destroy()`. New `LogTransport.flush()` and `Logger.flush()`.
- `StepGenerator` scans the `ClassRegistry` for the global steps once, also when the application has no global steps. Before, an application without global steps scanned the whole registry every time a plan was generated.
- The cached results and the rate limit buckets of two classes with the same name are no longer shared. `CacheProcessor` and `RateLimitProcessor` identify the class of the handler with the new `ClassIdentifier`: the first class registered with a name keeps the name, so the keys of applications without repeated names do not change, and the next ones get `<name>#<n>` in registration order, the same in every process of the application, so shared stores such as Redis keep working between replicas.
- The health checks can cache their results: new `cacheTtl` option of `@HealthCheck()` and of `HealthEngine.register()`, and `healthChecks.cacheTtl` in the application config for every check, so frequent probes do not hit the databases and brokers continuously. Concurrent health requests share the checks that are running.
- `HealthEngine` reads the health checks decorated with `@HealthCheck` from the `ClassRegistry` and their metadata once, on the first health check, instead of on every request to the health endpoints.
- The HTTP plugin only enables `HostGuard` when at least one controller declares a `host`, so applications without host routing run one step less per request.
- `InMemoryCacheStore` and `InMemoryRateLimitStore` remove the expired entries incrementally: each write or check examines a few entries (8), continuing from where the previous one stopped, instead of scanning the whole map every 256 operations, which created latency spikes with large maps.
- `ScopedContainer` creates its map of instances and its `PendingInstances` the first time a scoped provider is resolved, so the scoped container that the transports create for every execution allocates nothing else in applications without scoped providers.
- Fewer allocations per HTTP request: the Fastify adapter creates the session wrapper only when the session is read, and `HttpEngine` completes the context created by the adapter in place instead of copying it into a new object.
- `ResolutionChain.with()` no longer copies the array of steps for each dependency: the chain is linked to its parent, `hasSingleton()` is a flag computed when the chain is created, and `includes()` walks the links without allocating anything.
- `Logger` returns at once, without building the entry, merging the metadata or calling the transports, when the level is below the lowest `minLevel` of its transports, so the `debug` and `trace` calls cost almost nothing in production. New `Logger.isLevelEnabled(level)` and `LogTransport.minLevel`.
- The dependencies of a constructor, and the `inject` tokens of a factory provider, are resolved in parallel with `Promise.all`, so the asynchronous factories that a class needs run at the same time at startup and in scoped resolutions. The circular dependency and scope checks are kept: each dependency is resolved in a fork of the resolution chain, so dependencies of the same class can wait for the singletons created by each other.
- The plugins that do not depend on each other run `onRegister` and `onStart` at the same time, level by level of the dependency graph, so independent connections (Redis, Kafka, RabbitMQ) no longer start one after the other. `onStop` still runs one plugin at a time in the reverse of the dependency order, because a plugin can use the connections of another one without declaring it, such as the scheduler with a `RedisStore`. New `pluginLifecycle` option of the application: `'sequential'` keeps running them one by one in dependency order.
- `PipeProcessor` keeps the instances of the singleton pipe-steps after their first resolution, so each execution only resolves the scoped and transient pipe-steps with the injector. New `Injector.isSingleton(token)` and `Container.isSingleton(token)`, which check whether a token is bound to a singleton or a value, also through `useExisting` aliases.
- The cached `ExecutionPlan` of a handler no longer keeps the execution context of the first request, with its request, response, scoped container and signal, for the life of the process. The plan has a `handler` property with the class and the property key of the handler instead of `context`.

  Breaking changes: code that reads `plan.context` of an `ExecutionPlan` must read `plan.handler`, which only has `target` and `propertyKey`.
- `PluginRegistry` no longer stops the lifecycle of the remaining plugins when one plugin is in the `Error` state: the failed plugin is skipped and the rest of the plugins run their `onStart` and `onStop` methods, so their servers start and their connections are closed on shutdown. A plugin whose required dependency is in the `Error` state is skipped too, and moves to the `Error` state with the new `PluginDependencyFailedError`.
- The host patterns of the routes are normalized, split and scored once, when the routes are registered, instead of on every request. New `HostPattern` (exported by `@axisparkjs/http`) and `RouteDefinition.hostPatterns` / `RouteDefinition.hostSpecificity`; the request host is normalized and split once, in `HostDefinition.setHost()`.
- `HandlerInvoker` reads the parameters and the pipes of each handler from the metadata once, the first time the handler is invoked, instead of on every invocation of every step and handler. Each invocation only resolves the values of the parameters and runs the pipes.
- `RateLimitGenerator` generates the rate limit policy of each handler and transport once and keeps it, so the rate limited HTTP and WebSocket requests do not read metadata. The kept policies are discarded when `RateLimitGenerator.registerRateLimit()` changes the default policy of a transport.
- `HttpCacheResolver` reads the headers of `@CacheVary()` of each handler from the metadata once and keeps them, so the cached HTTP requests do not read metadata.
- `ExecutionPlanner` generates the plan of each handler exactly once, also when several requests reach a handler for the first time at the same time: the promise of the plan is cached and shared. A failed generation is removed from the cache, so the next request generates the plan again.
- `HttpEngine` skips the host and version matching for a route that is the only one of its method and path, accepts every host and has no versions (versioning disabled), which is the most common case. `context.host` and `context.version` are `undefined` for those requests, so `HostGuard` and `VersionGuard` have nothing to check.
- Resolving a singleton that is already created, or a value, no longer goes through several async functions: `Container.resolve()` and `Injector.get()` return it directly, without starting a resolution chain. New `Container.tryResolve(token)` and `Injector.tryGet(token)`, which return synchronously the value or the created singleton of a token, also through `useExisting` aliases, or `undefined` without creating anything.
- `HandlerInvoker` keeps the instances of the singleton middlewares, guards, interceptors, filters and handlers after their first resolution, so each execution only resolves the scoped and transient targets with the injector. New `Injector.isSingleton(token)` and `Container.isSingleton(token)`, which check whether a token is bound to a singleton or a value, also through `useExisting` aliases.
- `InMemoryRateLimitStore` uses a sliding window counter instead of a sliding log: each bucket keeps the requests of the current and the previous fixed window, so the cost and the memory of a client and handler are constant whatever the limit. It is an approximation of the sliding window: the requests of the previous window are taken as spread evenly over it, and the `retryAfterMs` of a rejected request is the time until the estimate leaves room for one more request.
- `ValidateSchemaPipeStep` reads the class of each parameter from the `design:paramtypes` metadata once per handler and parameter, instead of on every validation.

## 1.6.0 (2026-11-14)

### Features

- New application settings in `@axisparkjs/core`: the `settings` option of `AxiSparkFactory.create()` reads the environment variables and the `.env` files (`envFiles`, parsed with `util.parseEnv()` of Node.js, without new dependencies), converts them with the `EnvReader` given to `load` (`string`, `int`, `float`, `boolean`, `enum`, `url`, `json` and `list`) and validates them when the application is created. A variable without a default is required, and an invalid configuration throws one `InvalidSettingsError` that lists every problem, without printing the values of the rules that can involve secrets. The real environment variables win over the files, and the earlier files win over the later ones. The settings object is deeply frozen, typed from the return type of `load` in `app.settings` (available before `init()` to build the plugin options), and injected with the new `@EnvSettings()` decorator or the `AXISPARK_ENV_SETTINGS` token. `AxiSparkTestFactory.create({ settings })` of `@axisparkjs/test` replaces the settings without reading the environment, and reuses the settings already loaded by `app` when it is not given. The `caching-responses`, `shared-stores` and `sessions-and-cookies` samples read their port, Redis URL and secrets from the settings, and the templates of `axispark create` include a `.env.example`. Without the `settings` option, nothing changes.
- Every execution has an `AbortSignal` in the new `signal` property of `ExecutionContext`, injected in the handlers with the new `@Signal()` parameter decorator of `@axisparkjs/engine`. The `ExecutionEngine` creates it for each execution and aborts it with an `ExecutionTimeoutError` when the timeout ends, before the timeout resolver runs, so the handler stops while the `408` is being sent; the response of a timed-out execution does not change and a late result is discarded. It is also aborted with the reason of the signal of the transport: a new `ClientDisconnectedError` when the HTTP connection is closed before the response is sent (new optional `HttpRequest.signal`, implemented by the Express and Fastify adapters with the new `clientDisconnectSignal()` helper of `@axisparkjs/http`) or the WebSocket connection is closed (new optional `WebSocketConnection.signal`, implemented by the Socket.IO adapter with one listener per socket), and the reason of `McpRequest.signal` when the MCP client cancels the request. When the client stops waiting and the handler fails because of the abort, the error filters are skipped, so the error is not handled as a failure of the handler. The listener added to the signal of the transport is removed when the execution ends. Handlers that do not use the signal behave as before. Custom transports that build an `ExecutionContext` must now give a `signal` (their own, or any signal: the engine replaces it with the signal of the execution). The `versioning-and-timeouts` sample has slow reports that stop on timeout and on disconnection.
- New built-in pipe-steps in `@axisparkjs/engine`. `Default(value, { emptyString? })` gives a value to a missing parameter (objects and arrays are copied for each execution), and `Optional({ emptyString? })` skips the rest of the steps of a missing parameter so the handler receives `undefined`: a missing optional parameter no longer answers `400`. `ParseUuid(version?)` checks the UUID format (RFC 9562, versions 1 to 8) and returns it in lower case. `ParseEnum(enumOrValues, { ignoreCase? })` accepts a string or numeric TypeScript enum or an array of values and lists the allowed values in the error. `ParseDate({ dateOnly? })` converts an ISO 8601 date, or a date-time with `Z` or an offset, to a `Date`, and rejects invalid dates such as `2026-02-30` and date-times without an offset. `ParseArray({ separator?, items?, minItems?, maxItems?, unique? })` returns an array from a comma-separated string, a single value or an array, and applies the `items` step (such as `ParseInt()`) to each item. A pipe step can return the new `PipeStepSkip` value to stop the pipe of its parameter, and `PipeStep.execute()` receives the execution context as an optional third argument. The `validating-schemas` sample uses the new steps.
- New repository operations in `@axisparkjs/data`.

  **Breaking change:** a derived `findBy` method that receives a `PageRequest` now resolves with a `Page<T>` (`{ content, page, size, totalElements, totalPages }`) instead of `T[]`. The total is counted with the same predicates (`getManyAndCount()` in SQL, `countDocuments()` in MongoDB), so the extra `countBy` query is no longer needed. Read the entities from `page.content`, and declare the methods as `(…, page: PageRequest) => Promise<Page<T>>`. The methods without a `PageRequest` do not change.

  - `BaseRepository` has `findById(id)` (resolves with `null` when the entity does not exist), `findByIds(ids)`, `existsById(id)` and `deleteById(id)` (resolves with the number of deleted entities). They use the primary columns of the entity metadata, so they work with any column name and with composite keys (given as objects), and in MongoDB a hexadecimal string is converted to an `ObjectId`. `findPage(options, pageRequest)` returns a `Page` for queries that are not derived.
  - New derived query keywords: `Not`, `NotIn`, `Containing`, `StartingWith`, `EndingWith`, the `IgnoreCase` suffix (after a property or after `Not`, `Like`, `Containing`, `StartingWith` and `EndingWith`) and `True` / `False`. The values of `Containing`, `StartingWith` and `EndingWith` are escaped, so `%` and `_` are matched literally. `In` and `NotIn` with an empty array match nothing and everything instead of failing with `IN ()`.
  - New `deleteBy…` derived methods, with the same predicates as `findBy`, that resolve with the number of deleted entities and join the active transaction.

### Improvements and fixes

- `axispark create` downloads the templates from the `axisparkjs-org/axispark` repository (`https://github.com/axisparkjs-org/axispark/archive/refs/heads/main.tar.gz`), instead of depending on the redirect of the old `axisparkjs` organization name. The links of the README, the development guide and the pull request template point to the `axisparkjs-org` organization.
- `HttpResults.Download()` and `HttpResults.Stream()` build the `Content-Disposition` header as described by RFC 6266, with the new `contentDisposition(filename, type)` helper of `@axisparkjs/http`. The header has an ASCII fallback in `filename`, with the characters outside ASCII replaced with `?` and the double quotes escaped, and the name encoded in UTF-8 in `filename*` (RFC 8187) when it is not plain ASCII. A file name with quotes or accents is downloaded with its real name, a file name outside Latin-1 no longer fails with `500`, and the control characters and path separators of the name are removed, so a name taken from user data always produces a valid header.
- Cancelling a prompt of `axispark create` (Ctrl+C or Esc) stops the command with the message `Cancelled.` and the exit code `130`, before anything is written to disk, instead of failing with an internal error. Cancelling the "Install dependencies?" prompt, when the project already exists, continues without installing and shows the `npm install` step. The project name is validated while typing, and an invalid name is reported with the rule: `Invalid project name "…". Use only letters, numbers, "-" and "_".` The CLI prints the errors of the commands in one line, without a stack trace, and exits with the code `1`. The new `--verbose` option, or the `DEBUG` environment variable, prints the stack trace.
- Concurrent resolutions in the dependency injection container no longer throw false `CircularDependencyError` and `ScopeDependencyError`. Each resolution keeps its own resolution chain, passed as an argument through the container and the resolver instead of a stack shared by the resolver, so two resolutions that run at the same time never see the dependencies of each other. A singleton, or a scoped instance inside one scoped container, that is being created is shared by the concurrent resolutions, so it is created once and every resolution receives the same instance. When its factory fails, the next resolution tries again. Real circular dependencies and scope violations are still detected with the same messages, also between two concurrent resolutions that would wait for each other. The public signature of `Container.resolve()` does not change.
- The dependency injection `Container` and `ScopedContainer` store the providers and the scoped instances by the identity of their token instead of by its name. Two classes with the same name, such as `v1/UserService` and `v2/UserService`, resolve to their own instances, two `InjectionToken` with the same description are different tokens, and a token whose description is the name of a class no longer replaces the provider of that class. The execution plans of the engine are cached by the identity of the class too, so two controllers with the same name run their own handlers. A scoped factory that returns a falsy value (`0`, `''`, `false`) is created once per scoped container instead of on every resolution.

  `@axisparkjs/di` has a new `createTokenFactory(describe)` function, which returns the same token for the same key. The tokens of named connections use it, and are exported: `kafkaConnectionToken(name)`, `kafkaProducerToken(name)` and `kafkaConsumerToken(name)` in `@axisparkjs/kafka`, `rabbitMQConnectionToken(name)` in `@axisparkjs/rabbitmq`, and `dataSourceToken(name)` and `dataRepositoryToken(repository)` in `@axisparkjs/data`. `redisConnectionToken(name)` of `@axisparkjs/redis` returns the same instance for the same name.

  Breaking changes: code that creates a second `InjectionToken` with the same description to read the value of another token no longer finds it. Reuse the exported token, or the function that returns it, instead: for example `@Inject(redisConnectionToken('CACHE'))` instead of `@Inject(new InjectionToken('REDIS_CONNECTION_CACHE'))`.
- `useExisting` providers pass the scoped container to their target, so an alias of a `Scoped` class, such as an `InjectionToken` that points to a class, resolves inside a request instead of failing with `ScopedContainerNotProvidedError`. Inside one scoped container, the alias and its target are the same instance. An alias that points to itself, or a chain of aliases that points back to one of its tokens, throws `CircularDependencyError` instead of recursing until the stack overflows.
- The packages are compiled to ES2023 instead of ES2016, so the published code uses the native `async`/`await`, optional chaining, nullish coalescing, class fields and object spread. The stack traces point to the original methods instead of the `__awaiter` helper, and the asynchronous request pipeline runs without the generator wrappers. The packages now require a runtime with ES2023 support, already guaranteed by `"engines": { "node": ">= 24" }`. The class fields keep their current semantics (`useDefineForClassFields: false`), so the decorators and the DI container behave as before. The `tsconfig.json` of the templates generated by `axispark create` use the same target.
- `HttpResults.File()` and `HttpResults.Download()` send the file with the Fastify adapter, instead of answering `200` with an empty body. The route handler of the Fastify adapter returns the reply, so Fastify waits for the replies that are sent after the handler ends, which also fixes the empty body of `HttpResults.Stream()` with Fastify. The path of a file result means the same with both adapters: an absolute path, sent from its own folder, so it no longer depends on the `public` folder of the Fastify adapter. Both adapters keep the `Content-Type` set by the result and send the files inside folders that start with a dot.

  A missing file is answered with `404` in the JSON format of the framework with both adapters, instead of the HTML page of Express or an empty `200`. `HttpResponse.file()` returns a promise that resolves when the file is sent, and `FileHttpResult` waits for it.

  Breaking changes: `HttpResults.File()` and `HttpResults.Download()` throw an error for a relative path, which the filters answer with `500` and a message that explains it. Build the path with `path.join(__dirname, ...)`, for example. Custom implementations of `HttpResponse` must return a promise from `file()`.
- The HTTP plugin has a new `host` option, passed to `listen()` by the Express and the Fastify adapters. Without it, both adapters listen on every network interface, as Node.js does: `::` when IPv6 is available, and `0.0.0.0` otherwise. The Fastify adapter listened only on `localhost`, so an application that used it could not be reached from outside its container. The start message of the HTTP plugin shows the address and the port returned by the server, such as `Listening on [::]:3000`, so a wrong binding is visible in the logs.

  Breaking changes: applications that rely on the Fastify adapter being reachable only from `localhost` must set `host: '127.0.0.1'`.
- A stream error in `HttpResults.Stream()` no longer stops the process with the Express adapter. Both adapters send the stream with `pipeline()`, which destroys the response when the source fails and the source when the client closes the connection, and `HttpResponse.stream()` returns a promise that resolves at the end of the transfer and rejects with the error of the source. A stream that fails before sending any data is answered with `500` in the JSON format of the framework, with both adapters, and a stream that fails in the middle of the transfer closes the connection, so the client sees an incomplete transfer. The error is logged with the route by the HTTP logger when `logErrors` is enabled. The Fastify adapter sends the content of the streams, instead of an empty body.

  The errors that happen after the handler and the filters, while the response is sent, are logged by `HttpEngine` instead of being thrown to the adapter, and a response that has not started yet is answered with `500`.

  Breaking changes: custom implementations of `HttpResponse` must return a promise from `stream()`.
- A log transport that fails, such as an `HttpTransport` or a `WebhookTransport` whose endpoint is down, no longer rejects `logger.info()`, `warn()`, `error()`, `debug()`, `trace()` and `fatal()`. `Logger.log()` waits for every transport with `Promise.allSettled()`, so the other transports still receive the entry and the code that logs, awaited or not, is never broken by a log line. The failure of a transport is written to `process.stderr` at most once per transport every minute, or passed to the new `onError(error, entry)` option of the transport. The new `failOnError` option of the transports keeps the rejection for the logs that must stop the operation when they can not be written, such as audit logs.

  `HttpTransport` and `WebhookTransport` have a new `timeout` option, 5 seconds by default, so a log endpoint that does not answer can not block the application.
- The `package.json` of every package declares `repository` (with the folder of the package), `homepage`, `bugs` and `keywords`, so the npm page links to the source code, the website and the issue tracker. The production versions are published with provenance statements generated by GitHub Actions. Every package declares its public entry point in `exports`: importing the package (`@axisparkjs/http`) and its `package.json` work as before, but importing an internal file of `lib` (for example `@axisparkjs/http/lib/...`) now fails with `ERR_PACKAGE_PATH_NOT_EXPORTED`. Import everything from the package root. The published tarballs no longer contain `tsconfig.build.json`.

## 1.5.0 (2026-11-09)

### Features

- **Scanner include and exclude.** New `scanner` option in `AxiSparkConfig` with `include` and `exclude` glob patterns to choose the files that `FileSystemScanner` loads from `basePath`. The `exclude` patterns are added to the default exclusions, which now also ignore every bootstrap file (`*.bootstrap.{js,ts}`, not only `index.bootstrap`), the `*.test.{js,ts}` files and the `coverage` folder. The scanner logs the number of loaded files at `debug` level and each file at `trace` level. Applications that relied on the scanner importing bootstrap files other than `index.bootstrap` must import them explicitly.
- **Handler cache.** Cache of the handler results in `@axisparkjs/engine`, independent of the transport and kept in the `cache` store of `@axisparkjs/store`. A handler, or a class, decorated with the new `@Cache({ ttl?, key? })` returns its cached result while it is valid instead of running again, and `@NoCache()` disables the `@Cache()` of its class. The cache is opt-in: no handler is cached without `@Cache()`. The middlewares, guards and before interceptors run on every request, also on cache hits, and the after interceptors and the result processor run as usual, so a cached result produces the same response as a fresh one. Only plain results are cached: `undefined`, the `ResultDefinition` instances (`HttpResults.File()`, streams, redirects…) and the errors are not. When the store fails, the handlers run without cache and a warning is logged at most once a minute. The new `CacheService` evicts every result of a handler (`evict(ProductController, 'find')`) with a generation counter, or one entry (`evict(ProductController, 'find', key)`). The engine has the new `CacheDefinition`, `CacheGenerator`, `CacheResolver` and `CacheProcessor`, and `ExecutionPlan` has a new `cache` field.

  The HTTP plugin caches the `GET` and `HEAD` requests of the handlers with `@Cache()`, with a key made of the method, the host, the path and the sorted query string. The requests with an `Authorization` or `Cookie` header are not cached, unless the handler has a custom `key`, for example to cache per user. The new `@CacheVary('accept-language')` decorator adds request headers to the key. The new `cacheOptions` option sets the default `ttl` (60 seconds) and the `store` (`MemoryStore()` by default, or a shared store such as `RedisStore('MAIN')`), created when the plugin starts. New `caching-responses` sample.
- **Trusted proxies.** New `trustProxy` option in `HttpPluginOptions` to resolve the client address from the `X-Forwarded-For` header when the application runs behind a reverse proxy or a load balancer. It accepts `true`, the number of trusted proxies, or the addresses and subnets of the trusted proxies, and is passed to Express (`trust proxy` setting) and Fastify (`trustProxy` server option). It defaults to `false`, so `request.ip` and the rate limits keep using the socket address unless it is set.
- **Shared rate limiting.** The rate limit buckets and the sliding window move from `HttpRateLimitResolver` (`@axisparkjs/http`) to `RateLimitProcessor` (`@axisparkjs/engine`), so every transport counts requests with the same algorithm. The requests are counted per transport, client and handler in a new `RateLimitStore`, with the `InMemoryRateLimitStore` used by default and replaceable with `RateLimitProcessor.registerRateLimitStore()`. `RateLimitResolver.resolve(context)` now returns the client identifier instead of the decision, and `HttpRateLimitResolver` returns `request.ip`. HTTP rate limiting keeps the same options, decorators, `429` response and `Retry-After` header. Custom resolvers registered with `RateLimitProcessor.registerRateLimit()` must return the client identifier.
- **Redis.** New `@axisparkjs/redis` package with the `RedisPlugin`, which manages named Redis connections based on `node-redis`. The connections are configured with a name, a URL and the client options, injected with `@InjectRedisConnection(name)` or retrieved from the `RedisConnectionManager`, and closed when the application stops. The `ready`, `reconnecting`, `error` and `end` events are logged, and connection errors never stop the process. The clients connect in the background, so the application starts even when Redis is not available, and a `redis:<name>` health check is registered for each connection unless `healthChecks` is `false`.
- **Graceful scheduler shutdown.** The `SchedulePlugin` stops gracefully when the application stops: it stops scheduling new executions, aborts the signal of the running jobs, and waits for them, up to the new `shutdownTimeout` option (25 seconds by default with `SchedulePluginOptionsFactory`, `0` does not wait), before the next plugins are stopped. The `no-overlap` jobs that end during the shutdown release their locks while the lock store is still open, so another instance can run them right away. When the timeout ends first, a warning with the names of the jobs that are still running is logged, and the heartbeat of their locks is stopped, so the locks expire with their ttl once the process exits. Jobs receive an `AbortSignal` as their first argument, aborted when the job is stopped, so long jobs can end early between their steps. `SchedulerRunner` tracks the running executions, with a new `isExecuting(job)` method, and `SchedulerService` has a new `isJobExecuting(job)` method. A job that stops itself does not wait for its own execution.

  Breaking changes: `SchedulerService.stopJob()`, `SchedulerService.stopAllJobs()`, `SchedulerRunner.stop()` and `SchedulerRunner.stopAll()` return a `Promise<void>` that resolves when the running executions end, and accept the new `SchedulerStopOptions` (`timeout`). Without a `timeout`, they wait until the executions end. Code that calls them without `await` keeps working, but without waiting. `JobDefinition.execute(signal?)` passes the signal to the job function, typed as the new `JobFunction`.
- **Pluggable stores.** New `@axisparkjs/store` package with pluggable stores. Every feature that keeps state uses an in-memory store by default and accepts a `StoreProvider`, a function that the plugin calls with the kind of store it needs (`'rate-limit'`, `'lock'` or `'cache'`) when it starts. `MemoryStore()` provides `InMemoryRateLimitStore`, `InMemoryLockStore` and `InMemoryCacheStore`, and `RedisStore(connection, { prefix })` from `@axisparkjs/redis` provides `RedisRateLimitStore`, `RedisLockStore` and `RedisCacheStore`, which share the state between every instance connected to the same Redis. The HTTP rate limits accept `rateLimitOptions.store`, and the `SchedulePlugin` accepts a `lockStore` option, created with the new `SchedulePluginOptionsFactory`, for the new exclusive jobs: `@Cron({ value, exclusive: true })` runs each occurrence on only one instance, and `exclusive: { mode: 'no-overlap' }` never runs the job on two instances at the same time.

  Breaking changes: `RateLimitStore`, `RateLimitDecision` and `InMemoryRateLimitStore` move from `@axisparkjs/engine` to `@axisparkjs/store`, with no re-exports, and `HttpRateLimitResolver` no longer re-exports `RateLimitDecision`. `RateLimitStore.consume()` receives a `RateLimitPolicy` (`ttl` and `limit`), which `RateLimitDefinition` implements. `RateLimitProcessor.registerRateLimitStore(transport, store)` registers the store of one transport, so each plugin keeps its own store and never replaces the store of another one, and it has no in-memory default: register custom stores with `rateLimitOptions: { store: () => new MyStore() }` instead of calling it.
- **WebSocket rate limits.** Rate limits for the WebSocket events. The WebSocket plugin has new `rateLimit` and `rateLimitOptions` options (`ttl`, `limit`, `message`, `by` and `store`), as the HTTP plugin: with `rateLimit: true`, the new `WsRateLimitGuard` counts the events of each client per event handler, and the events beyond the limit are rejected with the new `WebSocketRateLimitExceededError` before the handler is invoked. The client receives it through the acknowledgement: `{ "error": "Too many requests. Please try again later.", "status": 429, "retryAfterMs": 750 }`. `@RateLimit()` and `@NoRateLimit()` work on WebSocket gateways and events as on HTTP controllers. The new `WsRateLimitResolver` identifies the clients with `rateLimitOptions.by`: `'address'` (default), so reconnecting does not reset the limits, `'connection'`, or a function, for example to count the events per authenticated user. The rate limits use the store of `rateLimitOptions.store` (`MemoryStore()` by default), created when the plugin starts, so the HTTP and WebSocket plugins can use different stores. `WebSocketError` has a new `details` getter, whose fields are added to the acknowledgement of the error.

  `WebSocketConnection` has a new `remoteAddress` property with the address of the client. The WebSocket plugin has a new `trustProxy` option, with the same values as the HTTP plugin, to resolve it from the `X-Forwarded-For` header of the handshake behind trusted proxies. It defaults to `false`, or to the `trustProxy` of the HTTP plugin with `useHttpPluginServer`. Breaking change for custom WebSocket adapters: their connections must implement `remoteAddress`.

### Improvements and fixes

- `ClassRegistry` stores the classes by identity instead of by name, so two decorated classes with the same name no longer replace each other. Applications that use the HTTP and WebSocket plugins together answer the HTTP errors with their status and body again, instead of an empty `200`, and two user classes with the same name, such as two `UserController` in different folders, are both registered. `ClassRegistry.remove()` only removes the given class, so disabling a framework component never removes a user class with the same name. `ClassRegistry` has a new `has(constructor)` method and a new `getAllByName(name)` method, which returns every class with that name.

  Breaking changes: `ClassRegistry.get(name)` is removed, because a name does not identify a single class. Use `ClassRegistry.has(constructor)` or `ClassRegistry.getAllByName(name)` instead. The `ReturnErrorFilter` of `@axisparkjs/websocket` is renamed to `WebSocketReturnErrorFilter`, as `McpReturnErrorFilter`.
- The cron job class of `@axisparkjs/schedule` is renamed from `CronJobDefinitio` to `CronJobDefinition`, the name used in the documentation. The old name is no longer exported: replace `CronJobDefinitio` with `CronJobDefinition` in your imports.
- `ExpressHttpAdapter.start()` resolves when the server is listening and rejects with the `listen` error (for example `EADDRINUSE`), so the application fails to start with a clear error instead of logging that it is listening and crashing later. `stop()` closes the idle keep-alive connections, resolves when the server is closed, and closes the connections that are still open after 10 seconds.
- `HttpTransport` sends the error of a log entry with its `name`, `message`, `stack` and `cause`, as `JsonFormatter` does, instead of an empty object. The rest of the entry keeps the same structure.
- The `@axisparkjs/logger` package documentation explains which transport is used when `logTransports` is not set, that the `ConsoleTransport` writes to the standard output, and how to write the logs to `stderr` with a `StreamTransport`, for example when using the MCP stdio transport.
- `@NoTimeout()` disables the timeout of a handler instead of making the request time out immediately. It defines `{ disabled: true }` in the timeout metadata instead of a time of `-1`, and `TimeoutGenerator` returns no timeout for a disabled metadata or a negative time. The method metadata still takes precedence over the class metadata, so `@NoTimeout()` on a method disables a `@Timeout()` of its class and the default timeout of the transport, and `@NoTimeout()` on a class disables the timeout of all its handlers unless a method has its own `@Timeout()`. `@Timeout(time)` throws an error when the time is not a number greater than `0`, so the mistake is visible at startup. `TimeoutMetadata.time` is now optional.
- The HTTP rate limit is applied per route instead of per requested URL: the bucket key is built with the client IP, the HTTP method and the handler, so changing a route parameter (`/users/1`, `/users/2`…) or the query string no longer bypasses the limit. `FastifyHttpRequest.path` returns the path without the query string, as `ExpressHttpRequest.path` does.
- Cron and interval jobs keep running when an execution takes longer than the time to the next one. The executions missed while the job was running are skipped, the next one is calculated from the current time, and a warning with the job name is logged. Two executions of the same job never overlap. `JobDefinition` and `JobTrigger` have a new `getNextExecutionTimeAfter(date)` method.
- Jobs whose next execution is more than ~24.8 days away (the maximum delay of a Node.js timer) no longer run in a loop: the `SchedulerRunner` waits with several timers and runs the job only at its scheduled time, so `@Cron(CronExpression.EveryYear)`, `@Cron(CronExpression.EveryMonth)` and long `@Interval()`, `@Date()` and `@Timeout()` jobs no longer print a `TimeoutOverflowWarning`.
- The `@Timeout()` of a WebSocket event acknowledges a timeout error to the client when the time ends, instead of leaving it without a response. `WebSocketPlugin` always registers `WebSocketTimeoutResolver`, which throws the new `WebSocketRequestTimeoutError` (`WebSocketError` with status `408`), and the `WebSocketReturnErrorFilter` sends it through the ack with the event name as its description: `{ "error": "Request timed out after 100ms", "status": 408, "description": "Event 'slow'" }`. The WebSocket plugin has new `timeout` and `timeoutOptions` (`time` and `message`) options, as the HTTP plugin: with `timeout: true`, every event has the default timeout, and `@NoTimeout()` disables it. `timeout` is `false` by default, and the Socket.IO `WebSocketPluginOptionsFactory` sets a default time of `5000` ms. `TimeoutProcessor` throws the new `ExecutionTimeoutError` from `@axisparkjs/engine` when no timeout resolver is registered for the transport, so the error filters of the transport handle the timeout instead of receiving an empty result.

  The `ReturnErrorFilter` of `@axisparkjs/websocket` is renamed to `WebSocketReturnErrorFilter`, as `McpReturnErrorFilter`, so it is no longer replaced by the `ReturnErrorFilter` of `@axisparkjs/http` in the `ClassRegistry`, which left the WebSocket errors without an acknowledgement. This is a breaking change only for code that imports the class by name.

## 1.4.0 (2026-11-03)

### Features

- **MCP server.** New `@axisparkjs/mcp` package with the `McpPlugin`, which exposes tools, resources and prompts to AI clients through the Model Context Protocol. Classes decorated with `@McpServer()` declare `@McpTool()`, `@McpResource()` and `@McpPrompt()` handlers that run through the `ExecutionEngine` (new `ExecutionTransport.Mcp`), receive `@McpArgs()`, `@McpParam()`, `@McpSession()` and `@McpContext()` parameters, and publish tool input schemas generated from their `class-validator` classes. The plugin serves stdio and Streamable HTTP, on its own port or mounted on the HTTP plugin server with `useHttpPluginServer`.
- **Custom health checks.** Custom health checks with the `@HealthCheck` decorator and `HealthIndicator` class, discovered automatically and run by `HealthEngine` in parallel with a timeout. `DataPlugin`, `KafkaPlugin` and `RabbitMQPlugin` register one health check per connection (disable with `healthChecks: false`). `HealthEngine.checkAll()` and `HealthEngine.checkApp()` are now asynchronous.
- **Data transactions.** Transactions in the Data plugin: the `@Transactional()` method decorator and the `TransactionManager` service run several repository calls in a single transaction. Every repository call made inside it joins the transaction automatically, including derived query methods.
- **Log metadata.** The `Logger` level methods accept an optional `metadata` argument (`info(message, metadata?)`, `error(message, error?, metadata?)`), and `child(scope, metadata?)` binds metadata that is merged into every entry of the child logger. `SimpleFormatter` prints the metadata, and `XmlFormatter` keeps metadata and stacks that contain `]]>` inside their CDATA sections.

### Improvements and fixes

- `axispark create` removes the project directory it created when copying the template or updating `package.json` fails, keeps the project when only the dependency installation fails, and rejects an unknown `--template` before downloading anything, listing the available templates.
- Derived repository methods match property names against the entity columns before reading `And`, `Or` and `OrderBy` as keywords, so properties such as `originCountry`, `orderId` or `androidVersion` are no longer split.
